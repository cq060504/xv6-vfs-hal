● LoongArch TLB Refill 逐行解读

  上下文：这段代码何时被调用

  CPU 执行 ld/st 指令，TLB 未命中
    → 硬件保存异常信息（TLBRBADV=故障VA, TLBREHI=故障VPPN）
    → 硬件设置 DA=1, PG=0（直接地址翻译模式，MMU 关闭）
    → 硬件跳转到 CSR.TLBRENTRY → tlb_refill_entry
    → 此时：低物理地址直接可达，所有寄存器必须手动保存/恢复

  ---
  第 1-5 行：文件头注释

  # LoongArch software TLB refill handler.
  # The CPU enters here through CSR.TLBRENTRY with DA=1/PG=0
  # The page-table layout is the four-level 9-9-9-9 scheme

  DA=1/PG=0 是关键：handler 自己访问内存时走直接地址翻译（VA=PA），不会触发递归 
  TLB miss。 所以 lddir 读页表时用物理地址。

  ---
  第 7-9 行：接受的 VA 范围

  # Accepted virtual addresses:
  #   User:   2*PGSIZE <= VA < MAXVA            (low half, via PGDL)
  #   Kernel: KSTACK_REGION_BOTTOM <= VA < KSTACK_TOP  (high half, via PGDH)

  两种合法地址：用户空间 [0x2000, 0x4000000000) 和内核栈 [0xFFFFFFFFFFFF3000, 
  0xFFFFFFFFFFFFF000)。

  ---
  第 11-13 行：段声明和入口

  .section .tlbrefill, "ax"   # 独立段，"a"=allocatable, "x"=executable
  .balign 4096                 # 必须 4KB 对齐（硬件要求 TLBRENTRY 页对齐）
  .globl tlb_refill_entry
  tlb_refill_entry:

  TLBRENTRY CSR 只接受页对齐的物理地址。这 4KB 专门给 refill
  handler，不和其他代码混用。

  ---
  第 14-16 行：保存临时寄存器

  csrwr   $t0, 0x8b              # TLBRSAVE ← 旧 $t0，$t0 ← 旧 TLBRSAVE

  csrwr 是"交换"：新 TLBRSAVE = 旧 $t0
                新 $t0 = 旧 TLBRSAVE（垃圾值，后面覆盖不关心）

  为什么只能用一个寄存器？
    TLB refill 可能打断任何内核代码。如果修改了 $t1/$a0 等，
    被中断的代码恢复后寄存器值就错了 → 随机崩溃。
    所以必须保存到 CSR 中（TLBRSAVE 专门为 refill handler 留的）。

  ---
  第 17-23 行：设置页大小

  csrrd   $t0, 0x8e              # t0 = TLBREHI
  srli.d  $t0, $t0, 6            # 右移 6 位，清除 PS 字段（bits[5:0]）
  slli.d  $t0, $t0, 6            # 左移 6 位，PS 字段变 0
  ori     $t0, $t0, 12           # 设置 PS = 12（4KB 页面大小）
  csrwr   $t0, 0x8e              # 写回 TLBREHI

  TLBREHI 寄存器布局：
    [63:13]: VPPN (虚拟页号) ← 硬件已设置
    [5:0]:   PS (Page Size)  ← 软件负责设置

  PS 含义：0=4KB, 6=16KB, 9=64KB, ..., 12=4KB (另一种编码)
  我们的页表所有页都是 4KB，所以统一设 PS=12。

  ---
  第 25-38 行：VA 合法性验证

  csrrd   $t0, 0x89              # t0 = TLBRBADV（引发 TLB miss 的 VA）

  blt     $t0, $r0, .Lchk_kern   # 有符号比较：VA < 0？即 bit63=1？

  # === 用户地址路径 ===
  srli.d  $t0, $t0, 13           # VA 右移 13 位
  beqz    $t0, .Ltlbr_invalid    # 结果=0 → VA < 0x2000 → 非法（guard 区）
  csrrd   $t0, 0x89              # 重读 TLBRBADV（$t0 被上一行破坏了）
  srli.d  $t0, $t0, 38           # VA 右移 38 位
  bnez    $t0, .Ltlbr_invalid    # 结果≠0 → VA >= MAXVA (0x4000000000) → 非法
  b       .Lrefill_ok            # 合法用户地址 → 继续 walk

  blt $t0, $r0 的判断逻辑：

  $t0 = VA, $r0 = 0
  有符号比较：$t0 < 0 意味着 bit63 = 1（负数）
    用户地址: 0x00000000_00002000 → bit63=0 → blt 不跳 → 走用户检查
    内核栈:   0xFFFFFFFFFFFFE000 → bit63=1 → blt 跳转 → 走内核检查

  VA 上下界检查（用户路径）：
    VA >> 13 == 0 → VA < 0x2000 → 访问了 NULL guard 区 → 拒绝
    VA >> 38 != 0 → VA >= 0x4000000000 → 超出 MAXVA → 拒绝
    合法：0x2000 <= VA < 0x4000000000

  ---
  第 40-50 行：内核栈地址范围检查

  .Lchk_kern:
          # KSTACK_REGION_BOTTOM = 0xFFFFFFFFFFFF3000
          # KSTACK_TOP          = 0xFFFFFFFFFFFFF000
          csrwr   $t1, 0x32              # 保存 $t1 → KSave2
          lu12i.w $t1, -13               # t1 = -13<<12 = KSTACK_REGION_BOTTOM
          bltu    $t0, $t1, .Ltlbr_kern_bad  # VA < BOTTOM → 非法
          lu12i.w $t1, -1                # t1 = -1<<12 = KSTACK_TOP
          bgeu    $t0, $t1, .Ltlbr_kern_bad  # VA >= TOP → 非法
          csrrd   $t1, 0x32              # 恢复 $t1

  为什么又要保存 $t1？对比需要两个寄存器：
    $t0 存着 VA，$t1 存常量。只用 $t0 无法同时持有两个值。

  lu12i.w $t1, -13：
    -13 << 12 = -53248 = 0xFFFFFFFFFFFF3000 → KSTACK_REGION_BOTTOM ✓

  lu12i.w $t1, -1：
    -1 << 12 = -4096 = 0xFFFFFFFFFFFFF000 → KSTACK_TOP ✓

  bltu = 无符号小于，bgeu = 无符号大于等于。
  用无符号比较是因为 KSTACK 区域的值非常大，无符号比较不会产生符号位干扰。

  合法内核栈地址：0xFFFFFFFFFFFF3000 <= VA < 0xFFFFFFFFFFFFF000

  ---
  第 52-54 行：选择页表根

  .Lrefill_ok:
          csrrd   $t0, 0x1B              # CSR.PGD：硬件自动选 PGDL 或 PGDH

  CSR.PGD (0x1B) 的自动选择：
    读 0x1B 时，硬件看 TLBRBADV[63]：
      bit63=0 → 返回 PGDL (用户页表 或 内核页表)
      bit63=1 → 返回 PGDH (固定 kernel_pagetable)

  一条 csrrd 替代了 if-else 分支。

  ---
  第 56-61 行：Level 3 (PGD) 页表 walk

  lddir   $t0, $t0, 3            # 读根表[VPPN[47:39]]
  andi    $t0, $t0, 1            # 检查 V 位（bit0）
  beqz    $t0, .Ltlbr_invalid    # V=0 → 缺页
  csrrd   $t0, 0x1B              # 重读 PGD（$t0 被 lddir 覆盖了）
  lddir   $t0, $t0, 3            # 重读 PTE
  addi.d  $t0, $t0, -1           # 清零 V 位 → 得到 Level-2 表 PA

  lddir rd, rj, level:
    rd = memory[rj + (VPPN >> (12 + 9*level) & 0x1FF) * 8]

    rj = $t0 = 根表 PA
    level = 3 → 用 VPPN[47:39] 作为索引
    → 读出 8 字节 PTE → 存入 $t0

  为什么读两次？
    第一次：读 PTE → 检查 V 位 → 确认有效
    第二次：读 PTE → 减 1 清零 V 位 → 得到纯物理地址
    lddir 覆盖了 $t0，所以需要重读 PGD 再 lddir。
    （不能用第一次的 PTE 因为 andi 破坏了它）

  第 63-70 行：Level 2 (PUD)

  lddir   $t0, $t0, 2            # 读 Level-2表[VPPN[38:30]]
  andi    $t0, $t0, 1
  beqz    $t0, .Ltlbr_invalid
  csrrd   $t0, 0x1B              # 重读根 PA
  lddir   $t0, $t0, 3            # 重新从根走到 Level-2 PTE
  addi.d  $t0, $t0, -1           # 得 Level-2 表 PA
  lddir   $t0, $t0, 2            # 读 Level-2 PTE
  addi.d  $t0, $t0, -1           # 清零 V → 得 Level-1 表 PA

  注意： Level 2 这里从根重新走了。原因是 lddir 覆盖了
  $t0，无法保留中间状态。每次需要重新从根表 PA 出发 → Level 3 → Level 2
  完整走一遍。

  第 72-81 行：Level 1 (PMD)

  lddir   $t0, $t0, 1            # 读 Level-1表[VPPN[29:21]]
  andi    $t0, $t0, 1
  beqz    $t0, .Ltlbr_invalid
  csrrd   $t0, 0x1B
  lddir   $t0, $t0, 3            # 根 → Level 3
  addi.d  $t0, $t0, -1
  lddir   $t0, $t0, 2            # Level 2
  addi.d  $t0, $t0, -1
  lddir   $t0, $t0, 1            # Level 1
  addi.d  $t0, $t0, -1           # → Level-0 叶子表 PA

  第 83-88 行：Level 0 (PTE) — 最终填入 TLB

  ldpte   $t0, 0                 # 读叶子表[VPPN[11:0] 偶页] → TLBRELO0
  ldpte   $t0, 1                 # 读叶子表[VPPN[11:0] 奇页] → TLBRELO1
  tlbfill                         # 把 TLBRELO0/1 + TLBREHI 写入 TLB 随机项

  csrrd   $t0, 0x8b              # 恢复 $t0
  ertn                            # 返回，重试故障指令

  ldpte vs lddir:
    lddir：读中间级 PTE，结果放在通用寄存器 $t0
    ldpte：读叶子级 PTE，直接写入 TLBRELO CSR，不经过通用寄存器

  TLB 组织的奇偶页：
    LoongArch TLB 每个条目覆盖一对 4KB 页面（偶页+奇页）
    ldpte 0 → TLBRELO0 (VA[12]=0 的页)
    ldpte 1 → TLBRELO1 (VA[12]=1 的页)
    即使只用到一页，也必须两个都读。

  第 90-101 行：无效路径

  .Ltlbr_kern_bad:
          csrrd   $t1, 0x32              # 恢复 $t1

  .Ltlbr_invalid:
          csrwr   $r0, 0x8c              # TLBRELO0 = 0 (V=0)
          csrwr   $r0, 0x8d              # TLBRELO1 = 0 (V=0)
          tlbfill                         # 填入 V=0 的 TLB 条目
          csrrd   $t0, 0x8b              # 恢复 $t0
          ertn

  为什么填入 V=0 的 TLB 条目而不是直接 panic？

  如果直接 panic → refill 上下文中 panic 很危险（只有 $t0 可用）
  如果什么都不填直接 ertn → 重试 → TLB 又 miss → 又进 refill → 无限循环

  填入 V=0 条目 → ertn → 重试 → 硬件看到 V=0 → 触发 PIL/PIS 异常
  → 正常异常处理路径 → EENTRY → kernelvec/usertrap → 妥善处理

  完整流程图

  CPU ld/st 触发 TLB miss
           │
           ▼
    TLBRENTRY → tlb_refill_entry
           │
           ├─ 保存 $t0 → TLBRSAVE
           ├─ 设置 TLBREHI.PS = 12 (4KB 页)
           ├─ 读 TLBRBADV → $t0
           │
           ├─ bit63 = 1？ ────Yes──→ .Lchk_kern:
           │                              ├─ 保存 $t1 → KSave2
           │                              ├─ 检查 VA ∈ [BOTTOM, TOP)
           │                              ├─ 恢复 $t1
           │                              └── 合法 → .Lrefill_ok
           │                              └── 非法 → .Ltlbr_kern_bad
           │
           └─ bit63 = 0 (用户)：
                  ├─ VA < 0x2000？──Yes──→ .Ltlbr_invalid
                  ├─ VA >= MAXVA？──Yes──→ .Ltlbr_invalid
                  └─ .Lrefill_ok
           │
           ▼
    .Lrefill_ok:
      csrrd PGD → 根 PA
      lddir Level3 → 查 V → lddir Level3 → -1 → Level-2 PA
      lddir Level2 → 查 V → 重走 L3→L2 → -1 → Level-1 PA
      lddir Level1 → 查 V → 重走 L3→L2→L1 → -1 → Level-0 PA
      ldpte 偶页 → TLBRELO0
      ldpte 奇页 → TLBRELO1
      tlbfill
      恢复 $t0 → ertn
           │
           ▼
    CPU 重试故障指令 → TLB 命中 → 成功！

    (或 .Ltlbr_invalid: 填 V=0 TLB → ertn → PIL/PIS → 异常处理)

  ---
  为什么 RISC-V 不需要这些？

  RISC-V 的硬件自动做完了所有 walk。 上面 ~100 行汇编，在 RISC-V 中是 CPU
  内部的一小片电路。

  对比：

  LoongArch TLB miss:
    CPU 硬件做的：          软件(tlb_refill_entry) 做的：
    ├─ 保存 ERA/PRMD/CRMD   ├─ 保存/恢复 $t0 $t1
    ├─ 写 TLBRBADV/TLBREHI  ├─ 设置页大小
    ├─ 跳转 TLBRENTRY       ├─ 检查 VA 合法性
    │                       ├─ 选择 PGDL 还是 PGDH
    │                       ├─ 四级 lddir walk (20+ 条指令)
    │                       ├─ 每级检查 V 位
    │                       ├─ ldpte + tlbfill
    │                       ├─ 处理无效路径
    │                       └─ ertn
    └── 就这么多了           └── 全部是软件

  RISC-V TLB miss:
    CPU 硬件做的：
    ├─ 读 satp → 根表 PA
    ├─ 硬件 3 级 walk (Sv39)
    ├─ 检查 V/R/W/X/U 权限
    ├─ 填入 TLB
    └─ 重试指令
    软件做的事：0 行代码。全部硬件自动完成。

  为什么两个架构选择了不同的路？

  RISC-V 哲学：硬件自动，OS 简单
    - RISC-V 定位是"精简指令集"，但页表 walk 被公认是必须加速的关键路径
    - Sv39 walker 只需要简单硬件状态机 + 几次内存读取
    - 对 OS 开发者友好：不需要写 TLB refill handler

  LoongArch 哲学：软件控制，更灵活
    - TLB refill 交给软件 → 页表格式由 PWCL/PWCH CSR 配置
    - 可以支持非标准页表（不同深度、不同索引宽度）
    - OS 可以为特定场景优化 walk（如大页预判）
    - 缺点：每个 TLB miss 要多跑 ~30 条软件指令
